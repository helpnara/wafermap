## 1. 배경과 문제 정의

### 1.1 EDS 테스트란

EDS(Electrical Die Sorting)는 FAB 공정이 완료된 웨이퍼를 조립(Assembly) 전에 웨이퍼 상태로
전기적 검사하는 단계다. 국내 메모리 업계 용어이며, 산업 일반 용어로는 Wafer Test / Probe Test /
CP(Chip Probe)에 해당한다. 본 프로젝트는 **가상 DRAM 제품**(§2.5.1)을 기준으로 시나리오를 구성한다.

전형적인 EDS 흐름:

| 단계 | 내용 | 산출물 |
|---|---|---|
| EDS #1 | DC Parametric — open/short, leakage 등 기본 전기특성 | Bin code |
| EDS #2 | Function Test — cell fail 검출 (DRAM은 cell array read/write 포함) | Fail bit map |
| Repair | Laser/e-Fuse repair — redundancy row/column으로 대체 | Repair log |
| EDS #3 | Post-repair verify | Bin code |
| EDS #4 | Burn-in / Retention·Refresh Stress / Speed grading | 최종 Bin sort |

각 die는 최종적으로 Bin code를 부여받는다. DRAM 특화 Bin 정의 예시:

| Bin | 의미 |
|---|---|
| Bin1 | Good |
| Bin2 | Open/Short (전기적 단선/단락) |
| Bin3 | Leakage (누설전류 초과) |
| Bin4 | Cell Fail (function test 실패, repair 후에도 잔존) |
| Bin5 | Refresh/Retention Fail (DRAM 특유 — capacitor 전하 유지 불량) |
| Bin6 | Speed Fail (AC parametric, burn-in 후 등급 미달) |

**die별 pass/fail을 웨이퍼 좌표에 배열한 것이 wafer map(bin map)** 이며, 본 프로젝트의 출발점이다.
분류 모델(M1)은 WM-811K 표준에 따라 pass/fail 이진 맵의 **공간 패턴**을 다루고, Bin 세부 분포는
`2_웨이퍼맵_탐색` 페이지에서 참고 정보로만 제공한다(패턴 라벨 자체는 WM-811K 원 라벨을 그대로 사용).

### 1.2 현업의 문제

Wafer map의 **공간적 패턴은 원인 공정의 지문(fingerprint)** 이다. 웨이퍼는 원판이고 대부분의
단위 공정은 회전 대칭(spin coating, CMP 연마, 플라즈마 식각)이거나 반경 방향 프로파일을 갖기
때문에, 불량이 중심/링/엣지/선형 등 **물리적으로 해석 가능한 형상**으로 나타난다.

그러나 현업에서는:
- 패턴 판정이 엔지니어 육안에 의존 → 판정자 간 편차, 대량 물량 시 누락
- 패턴을 봐도 **어느 스텝의 어느 설비**인지 특정하는 데 시간 소요 (수백 스텝 × 수십 설비)
- 원인 파라미터 규명이 경험칙에 의존, 정량적 개선 목표치 설정이 어려움

### 1.3 본 프로젝트가 푸는 것

```
[1] Wafer Map 구성      → EDS bin map 재구성 및 시각화
[2] 패턴 자동 분류      → 9종 불량 패턴 ML 분류 (이상 유형 판정)
[3] 이상 발생 시점 탐지 → SPC 관리도 기반 이상 구간 검출 (언제부터?)
[4] 이상 공정/설비 특정 → 커미널리티 분석 (어느 스텝, 어느 챔버?)
[5] 원인 인자 규명      → FDC 파라미터 수준 SHAP 기여도 (무엇이 문제?)
[6] 개선방안 + 기대효과 → 최적 운전구간 도출, 수율 개선분·ROI 추정 (어떻게 조치?)
```

## 2. 데이터 전략

### 2.1 핵심 제약

**공개 데이터 중 wafer map과 공정 설비 센서(FDC)가 실제로 연결된 데이터셋은 존재하지 않는다.**
또한 WM-811K 원본(`LSWMD.pkl`, 약 2GB)은 개발 컨테이너에서 직접 내려받을 수 없다(§2.3).

| 데이터셋 | 내용 | 한계 |
|---|---|---|
| WM-811K (MIR Lab) | 실제 fab의 wafer map 811,457장, 그중 172,950장 패턴 라벨(9종) | 공정/설비 정보 없음, 용량 큼 |
| UCI SECOM | 반도체 공정 센서 590개 × 1,567 lot, pass/fail | 센서 의미 익명화, wafer map 없음 |
| UCI SECOM 계열 | — | 두 데이터 간 조인 키 없음 |

### 2.2 채택 전략 — 실측 맵 + 물리 기반 합성 FDC

```
┌────────────────────────┐        ┌──────────────────────────────┐
│ WM-811K (실측)          │        │ FDC Simulator (합성)          │
│ · die-level bin map     │◀──조인──▶│ · 9개 공정 스텝, 설비/챔버    │
│ · 9종 패턴 라벨          │ lot/    │ · 파라미터 시계열·요약통계     │
│ · 811k wafer            │ wafer   │ · 패턴별 인과 섭동 주입        │
└────────────────────────┘  key    │ · ground truth 동시 생성       │
                                    └──────────────────────────────┘
```

**설계 원칙**

1. **맵은 실측, 공정은 합성** — 앱 전면에 이 사실을 명시(사이드바 배지 + 데이터 개요 페이지).
   포트폴리오에서 데이터 출처를 호도하지 않는 것이 신뢰성의 핵심.
2. **합성은 임의가 아니라 물리 기반** — 각 불량 패턴에 대해 반도체 공정 물리로 설명되는
   원인 스텝·파라미터를 문헌/현업 지식에 근거해 매핑하고(§2.4), 그 파라미터에만 섭동을 주입.
3. **난이도를 인위적으로 유지** — 교락 요인, 정상군 드리프트(위양성), 설명 불가 불량(위음성),
   챔버 간 baseline 편차, 시간에 따른 설비 노후화, 원인과 무관한 **distractor 스텝**(§2.5)을
   함께 주입해 분석이 자명해지지 않게 한다.
4. **Ground truth를 별도 보관** — `ground_truth.parquet`에 실제 주입한 원인 스텝/설비/파라미터를
   기록. 이를 **원인 규명 모델의 정답지**로 사용해 "원인 분석 정확도"라는 정량 지표를 제시한다.
   → 대부분의 유사 포트폴리오가 못 하는 차별점.

### 2.3 개발 순서 — 합성 우선, 로컬 실데이터 후속 [확정]

WM-811K 전체(약 2GB, 811,457장)는 크기가 크고, 현재 개발 컨테이너는 네트워크 정책상
pypi/npm만 허용되어 Kaggle/UCI/HuggingFace가 차단된다. 두 이유 모두로 **원본을 이 환경에서
직접 받지 않고, 합성 경로로 전체 파이프라인을 먼저 완성한다.**

| 단계 | 위치 | 내용 |
|---|---|---|
| **1차 (본 세션)** | 개발 컨테이너 | `synth_wafer.py`로 WM-811K와 **동일 스키마**의 합성 wafer map 생성 → 전체 파이프라인(M1~M6) 개발·테스트·성능 리포트 |
| **2차 (사용자 로컬)** | 사용자 PC | Kaggle API로 `LSWMD.pkl` 다운로드 → `scripts/download_wm811k.py` → `build_dataset.py --source real` 실행 → 실데이터 기준 모델 재학습·성능 재검증 |

데이터 소스는 앱 사이드바에서 `실측(WM-811K)` / `데모(합성)` 토글로 전환하며, **코드 경로는 완전히
동일**하다(`src/wafermap/data/loader.py`가 스키마만 보고 분기). 이 구조 덕분에 원본 없이 개발한
모든 모델·페이지가 사용자가 로컬에서 `LSWMD.pkl`을 `data/raw/`에 두는 순간 그대로 실데이터로 동작한다.

> 실데이터 전환 시 체크리스트는 `docs/06_local_validation.md`(M7 산출물)에 별도 정리한다:
> 라벨 분포 재확인 → 피처 재추출 → 모델 재학습 → macro-F1 재측정 → 합성 대비 성능 갭 문서화.

### 2.4 불량 패턴 ↔ 원인 공정 매핑 (도메인 코어)

시뮬레이터의 인과 규칙이자, 앱이 제시하는 진단 근거의 기반.

| 패턴 | 형상 | 물리적 기전 | 원인 스텝 | 핵심 FDC 파라미터 |
|---|---|---|---|---|
| **Center** | 중심부 집중 | 반경방향 제거율/증착율 프로파일이 중심에서 이탈 | CMP (P050) | `down_force`↑, `pad_life`↑, `center_zone_pressure`↑ |
| **Donut** | 중심 제외 링 | 중간 반경대 온도/플라즈마 밀도 불균일 | CVD (P030) | `susceptor_temp_mid_delta`, `precursor_flow` 변동 |
| **Edge-Ring** | 최외곽 링 | 엣지 배제영역 처리 이상, 챔버 edge ring 마모로 엣지 식각률 저하 | Etch (P020) | `edge_ring_rf_hours`↑, `chamber_pressure` drift, `edge_gas_ratio` |
| **Edge-Loc** | 가장자리 국부 | 웨이퍼 핸들링 접촉, 척 엣지 파티클/온도 국부 이상 | Cleaning (P060) / 핸들링 | `chuck_edge_temp_dev`, `particle_count`↑ |
| **Loc** | 국부 클러스터 | 파티클 낙하, 국부 디포커스 | Photo (P010) | `focus_offset` 이탈, `defect_adder_count`↑ |
| **Scratch** | 선형 긁힘 | CMP 슬러리 이물/패드 스크래치, 핸들링 긁힘 | CMP (P050) | `slurry_flow`↓, `conditioning_time`↓, `particle_count`↑ |
| **Random** | 산발 | 랜덤 파티클, 미세 오염 | 다중/미상 | 특정 인자 없음 (노이즈 baseline 상승) |
| **Near-full** | 대부분 fail | 설비 major fault, recipe 오적용, mask 오류 | Implant (P040) 등 | `dose` 30%+ 이탈, `recipe_id` 오적용 |
| **none** | 정상 | — | — | — |

> 이 매핑은 시뮬레이터가 "심는" 정답이자, 커미널리티/SHAP 분석이 **독립적으로 다시 찾아내야 하는**
> 대상이다. 앱의 규칙 기반 힌트에는 이 표를 노출하되, 모델 결과는 데이터에서만 도출한다.
> `P045(Capacitor Formation, §2.5)`는 어떤 패턴과도 인과관계가 없는 **distractor 스텝**으로 두어,
> 커미널리티 분석이 우연한 상관을 얼마나 걸러내는지 보여주는 장치로 쓴다.

### 2.5 가상 공정 플로우 (합성 FDC)

#### 2.5.1 제품 프로파일 [확정: DRAM]

| 항목 | 값 |
|---|---|
| 제품 | 가상 DDR5 DRAM, 16Gb density |
| 공정 노드 | 1z-nm급 (가상) |
| 웨이퍼 규격 | 300mm |
| Die size (가정) | 약 4.5mm × 9.0mm |
| Gross die/wafer | 약 1,750 (WM-811K 실측 맵의 die 배열을 그대로 쓰므로 참고값) |
| Lot 구성 | 25 wafer/lot, slot 1~25 |

#### 2.5.2 공정 스텝

| Step | 공정 | 설비 (챔버) | 주요 파라미터 |
|---|---|---|---|
| P010 | Photo / Litho | SCAN-01~03 | focus_offset, exposure_dose, overlay_x/y, bake_temp, ebr_width |
| P020 | Etch | ETCH-A/B/C (ch1~4) | rf_power, chamber_pressure, cf4_flow, o2_flow, electrode_temp, endpoint_time, edge_ring_rf_hours |
| P030 | Thin Film / CVD | CVD-01/02 | dep_temp, precursor_flow, chamber_pressure, thickness_mean/sigma, susceptor_temp_mid_delta |
| P040 | Implant | IMP-01/02 | dose, energy, beam_current, tilt_angle |
| P045 | **Capacitor(Storage Node) Formation** — DRAM 특화 | CAP-01/02 | dielectric_thickness(HfO2), node_profile_cd, anneal_temp — *distractor, 어떤 패턴과도 인과 없음* |
| P050 | CMP | CMP-01/02 (head1~4) | down_force, platen_speed, slurry_flow, pad_life, conditioning_time, removal_rate, center_zone_pressure |
| P060 | Cleaning | CLN-01/02 | chem_conc, bath_temp, di_resistivity, particle_count, chuck_edge_temp_dev |
| P070 | Diffusion / Anneal | DIFF-01 | furnace_temp_z1~z3, ramp_rate, o2_flow |
| P080 | Inline Metrology | MET-01 | cd_mean/sigma, thickness, overlay_residual |

- Lot 단위로 스텝별 설비/챔버가 배정된다(현업과 동일, lot dispatching 시뮬레이션).
- Slot 위치 효과(엣지 슬롯 열 이력 차이)를 약하게 부여 → 슬롯 상관 분석 소재.
- 설비별 baseline 편차 + 시간 드리프트(PM 주기 톱니파) 주입 → 커미널리티/트렌드 분석 소재.
- P045는 DRAM 공정 리얼리티를 더하는 동시에 **분석이 우연히 맞히는 것을 방지하는 노이즈 스텝**으로 기능.

### 2.6 데이터 스키마

```
data/processed/
├─ wafer_master.parquet      # 웨이퍼 1행
│    wafer_id, lot_id, slot_no, product, tech_node,
│    fab_in_time, eds_time, die_total, die_pass, yield_pct,
│    pattern_label, map_path, data_source(real|synthetic), is_labeled
├─ die_map.npz               # wafer_id → 2D int8 array (0=no die, 1=pass, 2=fail)
├─ fdc_summary.parquet       # (wafer_id, step_id) × 파라미터 wide
│    wafer_id, step_id, step_name, equip_id, chamber_id, recipe_id,
│    <param>_mean, <param>_std, <param>_min, <param>_max, run_time
├─ fdc_trace.parquet         # 주요 파라미터만 시계열 (long)
│    wafer_id, step_id, param, t_sec, value
└─ ground_truth.parquet      # 합성 정답지 (검증 전용, 분석 모델 입력 금지)
     wafer_id, true_root_step, true_root_equip, true_root_params(list),
     severity, is_confounded, is_unexplained
```

> `is_labeled` 컬럼은 §11 백로그(미라벨 데이터 확장)를 위해 1차부터 스키마에 반영해 둔다
> (지금은 전량 `True`; 미라벨 확장 시 `False` 레코드가 추가되는 구조).

## 3. 분석·모델 설계

### M1. Wafer Map 패턴 분류

**범위 [확정]**: 라벨이 있는 WM-811K 172,950장(합성 단계에서는 동일 분포로 생성한 라벨 데이터)만
1차로 사용한다. 미라벨 638,507장 활용은 §11 백로그로 이월.

**입력** die-level bin map (가변 크기) → 64×64 정규화 그리드 (die-aware 리샘플링, 웨이퍼 외곽 마스크 보존)

**피처 (LightGBM용, 약 90차원)**

| 그룹 | 피처 |
|---|---|
| 기본 | fail_ratio, die_total, 웨이퍼 반경, 결측 die 비율 |
| 반경 프로파일 | 10개 동심 링별 fail rate, 링간 기울기, 최외곽/내부 비 (Edge-Ring 판별 핵심) |
| 각도 프로파일 | 12개 섹터별 fail rate, 각도 분산, 최대 섹터 비 |
| 밀도 | 13-zone density (Wu et al. 2015 표준 피처) |
| 기하 모멘트 | Hu moment 7종, 중심 편심도, 관성 반경 |
| 연결성분 | cluster 수, 최대 cluster 면적/이심률/solidity/장축비 (Loc·Scratch 판별) |
| Radon | Radon 변환 행 평균의 cubic interp 20점 + 표준편차 20점 (Scratch·Donut 판별, 원논문 방식) |

**모델**

- 주 모델: **LightGBM multiclass** (9 class). 극심한 불균형(none 147k vs Near-full 149) 대응 →
  class_weight balanced + macro-F1 최적화 + stratified 5-fold CV
- 비교군: **경량 CNN** (4 conv block, 64×64×1 입력, ~200K params, PyTorch CPU 학습 가능 규모) + Grad-CAM
- 평가: macro-F1(주지표), per-class recall, confusion matrix, PR curve, 추론 지연시간
- 해석: LGBM SHAP(어떤 기하 피처가 판정을 만들었나) vs CNN Grad-CAM(어디를 보았나) 병렬 제시

> **불균형 처리 방침**: 오버샘플링은 리크 위험이 있어 fold 내부에서만 적용. Near-full처럼 149장뿐인
> 클래스는 augmentation(회전·미러 — 웨이퍼는 회전 대칭이므로 물리적으로 타당)으로 보강.

### M2. 이상 발생 시점 탐지 (SPC)

- 시간축: `eds_time` 기준 일/시프트 단위 집계
- 관제 지표: 전체 수율, 패턴별 발생률, 설비별 수율
- 기법: **EWMA 관리도**(λ=0.2) + **CUSUM**(작은 시프트 민감) 병행, 관리한계 3σ
- 산출: 이상 구간(alarm 시작~해제) 자동 검출 → 이 구간의 wafer 집합을 **이상군(case)**,
  직전 안정 구간을 **정상군(control)** 으로 정의 → M3의 입력

### M3. 이상 공정·설비 특정 (커미널리티 분석)

현업 불량 분석의 표준 절차를 그대로 구현.

1. 이상군 vs 정상군에 대해 **스텝 × 설비/챔버** 교차표 생성
2. Fisher exact test (기대빈도 5 미만 셀 대응) 또는 chi-square
3. 효과크기: **odds ratio** + 95% CI, `lift = 이상군 통과율 / 정상군 통과율`
4. 다중검정 보정: **Benjamini-Hochberg FDR** (수백 개 설비를 동시 검정하므로 필수)
5. 랭킹 출력 예시:

   > `ETCH-B / ch3` — 이상군 통과 68/80(85.0%) vs 정상군 41/400(10.3%) · OR 45.9 (CI 23.1–91.2) · p_adj = 3.1e-27

6. 교락 통제: 상위 후보에 대해 다른 스텝 설비를 층화한 Cochran–Mantel–Haenszel 검정으로
   "정말 이 설비인가, 같이 흘러간 다른 설비 때문인가" 구분

### M4. 원인 인자 규명 (FDC 파라미터 수준)

- **타깃**: (a) 해당 패턴 발생 여부(binary), (b) wafer yield(regression) — 두 관점 병행
- **입력**: M3에서 특정된 스텝의 FDC 요약 통계 + 설비/챔버/recipe 범주형
- **모델**: LightGBM + **SHAP**
  - Global: mean|SHAP| 기여도 랭킹
  - Local: 개별 wafer의 force plot → "이 웨이퍼는 edge_ring_rf_hours=412h가 불량확률을 +0.38 올렸다"
  - Dependence: 파라미터 값 ↔ 불량확률 관계 곡선 (임계점 시각화)
- **통계 보조**: 이상/정상군 파라미터 분포 비교 (KS test, PSI, Cliff's delta)
- **인과 주의**: 상관 ≠ 인과 경고를 UI에 명시. 설비를 고정한 **층화 분석**으로 교락 최소화.
  (DoWhy 등 본격 인과추론은 범위 외 — 데이터 생성 구조상 과잉)
- **검증**: `ground_truth.parquet`와 대조하여
  - Root step 적중률 (Top-1 / Top-3)
  - Root parameter 적중률 (Top-5 SHAP 내 정답 파라미터 포함률)
  → **"원인 분석 정확도 87%" 같은 정량 성과**를 포트폴리오 지표로 제시

### M5. 개선방안 및 기대효과

1. **최적 운전 구간 도출**: SHAP dependence / partial dependence에서 불량확률이 최소인 구간을
   탐색 → 파라미터별 권고 spec 제안 (예: `CMP down_force 3.20–3.55 psi`, 현 spec 3.0–4.0 대비 tightening)
2. **조치안 템플릿** (패턴별 자동 생성 + 편집 가능)
   - 설비 PM 주기 단축 (예: edge ring 교체 400h → 300h)
   - 파라미터 spec tightening 및 SPC 인터락 설정
   - 챔버 매칭(chamber-to-chamber) 튜닝
   - 계측 샘플링 강화 구간 지정
3. **기대효과 시뮬레이션**: 제안 spec 내로 파라미터를 clip한 반사실(counterfactual) 입력을
   학습 모델에 통과시켜 예측 수율 변화 산출. **가정(모델 외삽 한계, 인과 가정)을 명시적으로 표기.**
4. **ROI 추정 [확정: 기본값 + 앱 내 조정]** — 사용자가 정확한 시세를 모르므로, 공개 자료 기반의
   보수적 가정치를 기본값으로 넣고 **`6_개선방안_기대효과` 페이지 사이드바에서 슬라이더/입력창으로
   즉시 조정** 가능하게 만든다. 값을 바꾸면 연간 절감액이 실시간 재계산된다.

   | 파라미터 | 기본값(가정) | 근거/비고 |
   |---|---|---|
   | wafer 1장당 가치 | 500만원 (가정) | 공정원가+양품 매출 기여분 추정치. 실측 아님 — 툴팁에 "가정치, 사내 원가자료로 교체 권장" 명시 |
   | 월 투입 웨이퍼 수 | 3,000장 (가정) | 중소 팹 라인 규모 가정 |
   | 개선 적용 수율 향상분 | M5.3 시뮬레이션 결과값 사용 | 데이터 기반 산출 |
   | 적용 스텝 수 | 사용자 선택(1개 이상) | UI에서 다중 선택 가능 |

   계산식: `연간 절감액 = 월 투입 웨이퍼 수 × 12 × 수율 향상분(%p) × wafer 1장당 가치`
   모든 가정치 옆에 출처/성격(가정 vs 데이터 기반) 배지를 표시해 신뢰성을 관리한다.

### M6. 신규 웨이퍼 실시간 스코어링

맵 업로드(또는 데이터셋 내 선택) → 패턴 예측 → 원인 후보 Top-3 스텝/설비 + 조치 가이드 즉시 출력.
현업 적용 시나리오를 보여주는 데모 페이지.

### 4.2 UX 원칙

- **언어**: 한국어 UI. 공정 용어는 현업 표기 유지(EDS, FDC, Bin, Lot, CMP …)
- **서사 흐름**: 페이지 번호 순서가 곧 분석 스토리. 각 페이지 하단에 "다음 단계" 안내 버튼
- **드릴다운 일관성**: 사이드바 전역 필터(기간·제품·스텝)를 `st.session_state`로 페이지 간 공유
- **데이터 출처 배지**: 모든 페이지 사이드바에 `맵: 실측 WM-811K / 공정: 합성` 배지 상시 노출
- **성능**: `@st.cache_data`(데이터·피처), `@st.cache_resource`(모델). 무거운 학습은 사전 수행 후
  아티팩트 로드만 수행 — 앱 내 학습은 금지(클라우드 메모리 한계)
- **반응형**: 데스크탑/태블릿/모바일 3단 브레이크포인트. 네비게이션은 전체/아이콘 레일/모바일
  아이콘 바 3-모드로 접어 표시 영역을 확보한다 (§4-A)

### 4.4 전역 상태 계약 (Session State)

페이지 간 이동 시 "무엇을 선택했었는지"가 유지되지 않으면 사용자가 매번 처음부터 다시 찾아야
한다. 아래 키를 `st.session_state`에 고정 정의하고, **하위 페이지는 상위 선택이 비어 있어도 항상
합리적 기본값으로 동작**하도록 설계한다(빈 화면 금지 원칙).

| 키 | 설명 | 기본값 | 설정 주체 |
|---|---|---|---|
| `data_source` | `synthetic` \| `real` | `synthetic` (Cloud는 강제 고정) | 전역 사이드바 |
| `date_range` | 분석 대상 기간 | 최근 90일 | 전역 사이드바 |
| `selected_wafer_id` | 상세히 볼 웨이퍼 | 없음 → 페이지별 대표 샘플 1장 자동 선택 | `2_웨이퍼맵_탐색` |
| `selected_alarm_id` | 원인 분석 대상 이상구간 | 없음 → **가장 최근 alarm 자동 선택** + 안내 배너 | `4_이상공정_탐지` |
| `selected_equip_candidate` | 커미널리티 랭킹에서 고른 설비 | 없음 → 랭킹 1위 자동 선택 | `5_원인_분석` |
| `roi_inputs` | wafer 단가·월 투입량 등 | §3 M5.4 기본 가정치 | `6_개선방안_기대효과` (초기화 버튼 제공) |
| `view_mode` | `desktop` \| `mobile` | User-Agent 추정값 | 전역 토글 — **URL 쿼리에도 기록**(§4A.2) |
| `nav_mode` | `full` \| `rail` \| `hidden` | 뷰포트별 기본값 | 사이드바 `⟨⟩` 토글 |
| `learning_pos` | 학습노트 위치(`note`, `card`) | 없음 | `8_도움말_학습` — URL 쿼리로 진도 이어보기(§4A.6) |

안내 배너 예시(하위 페이지를 상위 선택 없이 바로 열었을 때):
`ℹ️ 현재 "최근 이상구간"을 자동으로 표시하고 있습니다. 4_이상공정_탐지에서 다른 구간을 고르면 이 페이지가 바로 갱신됩니다.`

| 페이지 | 레이아웃 |
|---|---|
| `1_데이터_개요` | 상단 계층 다이어그램(lot→wafer→die) → 2열: 스키마 사전 테이블 \| 결측·이상치 요약 카드 |
| `2_웨이퍼맵_탐색` | 상단 검색/필터 바(패턴·기간·설비) → 썸네일 갤러리(그리드, **페이지당 20장 페이지네이션**, 172,950장 전체 로드 금지) → 클릭 시 하단에 확대 뷰 + 반경/섹터 오버레이 토글. **Bin 상세(§1.1)는 실측이 아닌 합성 예시 배지를 붙여 pass/fail 실측 라벨과 구분 표시** |
| `3_패턴_분류_모델` | 상단 지표 카드(macro-F1 등) → 좌:혼동행렬 \| 우:클래스별 recall 바차트 → 하단 탭(LGBM SHAP \| CNN Grad-CAM) |
| `4_이상공정_탐지` | 상단 EWMA/CUSUM 관리도(전체 폭) → alarm 목록 테이블(행 클릭 시 `selected_alarm_id` 갱신 → "5_원인_분석으로 이동" 버튼 활성화) |
| `6_개선방안_기대효과` | 좌: 조치안 카드 리스트(패턴별) \| 우: 반사실 시뮬레이터 + ROI 계산기(입력 슬라이더, 실시간 재계산, "기본값 재설정" 버튼) |
| `7_모델_검증` | ground truth 대비 적중률 카드 → 상세 비교 테이블 → 한계·가정 서술 섹션(항상 펼침, 축소 불가 — 신뢰성 핵심이라 숨기지 않음) |
| `8_도움말_학습` | 좌: 마일스톤 트리 \| 우: 탭(개념/코드/설계노트/확인문제), §5.5 참조 |

### 4.6 로딩 · 빈 상태 · 에러 UX

- **무거운 연산**(SHAP 전 구간 계산, CNN 추론)은 기본적으로 **사전 계산된 아티팩트**를 로드하고,
  사용자가 새 조건으로 재계산을 요청할 때만 `st.spinner` + 예상 소요시간을 표시한다.
- **빈 상태**: 필터 결과 0건이면 빈 차트를 그대로 보여주지 않고 `조건에 해당하는 웨이퍼가 없습니다`
  안내와 `필터 초기화` 버튼을 제시한다.
- **에러/폴백**: 로컬 실측 데이터 파일이 없는 상태에서 `실측` 토글을 시도하면 즉시 차단하지 않고,
  `실측 데이터가 아직 없습니다 → §2.3 절차대로 준비하기` 안내와 함께 합성 데이터로 자동 폴백한다.

### 4.7 데이터 소스 전환과 캐시 무효화

`data_source`는 `@st.cache_data`/`@st.cache_resource` 캐시 키에 항상 포함시켜, 토글 시 캐시를
전부 지우지 않고도 소스별로 자동 분리되게 한다. 전환 직후에는
`데이터 소스가 합성 → 실측으로 전환되었습니다. 모델은 실측 기준 사전학습 아티팩트를 사용합니다`
같은 배너를 짧게 노출해 "왜 결과가 달라졌는지" 혼동을 막는다.

### 4.8 색상·접근성

- 웨이퍼맵 pass/fail은 red/green 대신 **blue(정상) / orange(불량)** 계열(색약 친화 diverging
  팔레트)을 기본으로 하고, 색 외에 명도 대비·범례 텍스트를 항상 병기한다.
- 커미널리티 랭킹·SHAP 등 수치 강조는 색상 단독이 아니라 굵기/아이콘(⚠️, ✅)을 함께 사용한다.

### 4.9 온보딩 — 첫 화면 가이드

포트폴리오는 처음 보는 사람(채용 담당자 등)이 각 페이지를 스스로 탐색할 여유가 없는 경우가
많다. `app.py` 상단에 **`🎬 3분 가이드 투어`** 버튼을 두어, 클릭 시 사전 지정된 대표 이상 사례
(대표 wafer·alarm)로 `selected_alarm_id` 등 세션 상태를 프리셋하고 1→7번 페이지를 순서대로
안내한다. 이를 통해 클릭 없이도 "데이터 → 탐지 → 원인 → 개선" 전체 스토리를 빠르게 볼 수 있다.

### 4.10 맥락형 학습 노출 (학습 메뉴와 연결)

§5의 `8_도움말_학습` 페이지는 모듈 전체를 훑는 용도지만, 그것만으로는 "지금 보고 있는 이
화면이 어떻게 만들어졌는지" 바로 알기 어렵다. 이를 보완하기 위해 **1~7번 각 페이지 하단에
접힌 `st.expander("🎓 이 화면은 어떻게 만들어졌나요?")`** 를 배치한다. 펼치면 해당 페이지와
직결된 학습노트 핵심 3줄 요약 + "전체 학습노트 보기" 링크(8번 페이지 해당 항목으로 이동)를
보여준다. 기본은 접힘 상태라 포트폴리오 열람 시 시각적으로 방해되지 않는다.

## 4-A. 반응형 · 모바일 설계

> **동기** 이 앱은 두 가지 용도로 쓰인다. ① 데스크탑에서의 분석·포트폴리오 시연,
> ② **모바일에서 틈틈이 코드를 복습하는 학습 교재**(§5). ②는 이동 중·짧은 시간에 소비되므로,
> 데스크탑 화면을 그대로 축소하는 방식으로는 성립하지 않는다. 별도의 레이아웃 전략이 필요하다.

### 4A.1 Streamlit의 실제 제약 (검증 결과)

설계 전 Streamlit 1.40 패키지를 직접 확인해 아래를 사실 확인했다.

| 확인 항목 | 결과 | 설계 반영 |
|---|---|---|
| `st.navigation(position="hidden")` | **지원됨** — 기본 네비게이션을 숨기고 자체 UI로 대체 가능 | 아이콘 레일/모바일 아이콘 바를 CSS 해킹 없이 정공법으로 구현 (§4A.3) |
| `st.Page(title=, icon=, url_path=)` | 지원됨 | 페이지 메타데이터를 한 곳에서 선언, 네비게이션 3종이 동일 소스 참조 |
| `pages/` 디렉터리 + `st.navigation` 동시 사용 | **경고 발생** — *"st.navigation was called in an app with a pages/ directory. This may cause unusual app behavior. You may want to rename the pages/ directory."* | **`pages/` → `views/` 로 변경** (§6). 기존 설계의 디렉터리명을 수정 |
| `st.context.headers` | 지원됨 (User-Agent 접근 가능) | 최초 진입 시 모바일 여부 추정에 사용 |
| `st.query_params` | 지원됨 | 뷰 모드·학습 진도를 URL에 보존 (§4A.6) |
| 뷰포트 **폭**을 읽는 네이티브 API | **없음** | CSS 미디어쿼리를 주력으로 쓰고, 파이썬 분기는 UA 추정 + 수동 토글로 처리 (§4A.2) |

### 4A.2 브레이크포인트와 뷰포트 판별 전략

레이아웃 변경은 두 층으로 나눈다. **CSS로 되는 것은 전부 CSS로** 처리하고(항상 정확),
파이썬 레벨의 구조 변경(예: 2단 컬럼 → 탭)만 뷰 모드 플래그로 분기한다.

| 계층 | 담당 | 방식 |
|---|---|---|
| **시각 계층** (여백, 폰트, 차트 높이, 테이블 스크롤, 터치 타깃) | `assets/mobile.css` | `@media (max-width: 768px)` 미디어쿼리. 1회 주입, 항상 정확 |
| **구조 계층** (컬럼↔탭, 네비게이션 형태, 갤러리 장수) | `src/wafermap/ui/responsive.py` | `view_mode` 플래그로 파이썬 분기 |

`view_mode` 결정 순서 (뒤가 우선):
1. `st.context.headers["User-Agent"]` 로 모바일 추정 → 초기 기본값
2. URL 쿼리 파라미터 `?view=mobile|desktop` → 사용자가 명시 지정한 값
3. 화면 내 토글(`📱`/`🖥`) 클릭 → 즉시 반영하며 **쿼리 파라미터에 기록**

> 쿼리 파라미터에 기록하는 이유: `st.session_state`는 새로고침 시 사라진다. 모바일에서
> **홈 화면에 바로가기로 추가**(§4A.6)해 두면 `?view=mobile` 이 포함된 URL이 저장되어,
> 열 때마다 모바일 레이아웃으로 곧장 진입한다.

| 브레이크포인트 | 폭 | 레이아웃 |
|---|---|---|
| Desktop | ≥ 1200px | 사이드바 전체 표시(라벨+아이콘), 다단 컬럼 |
| Tablet | 768–1199px | 사이드바 **아이콘 레일**, 컬럼 2단까지 허용 |
| Mobile | < 768px | 사이드바 숨김 + **상단 아이콘 바**, 전부 단일 컬럼/탭 |

### 4A.3 내비게이션 3-모드 — "아이콘으로 접어 화면을 넓히기"

`st.navigation(position="hidden")` 으로 기본 네비게이션을 끄고, 아래 3가지 모드를 자체 렌더링한다.
모드는 사이드바 상단 토글 버튼(`⟨⟩`)으로 순환 전환하며 `view_mode` 와 함께 URL에 보존된다.

```
[A] 전체 모드 (Desktop 기본)        [B] 아이콘 레일 (Tablet 기본)   [C] 모바일 (< 768px)
┌──────────────┬──────────────┐   ┌──┬─────────────────────┐   ┌──────────────────────┐
│ ⟨ 접기        │              │   │⟩ │                     │   │ 🏠📊🗺🧠🚨🔎💡📈🎓 ← 상단│
│ 🏠 개요       │              │   │🏠│                     │   │    아이콘 바 (가로 스크롤)│
│ 📊 데이터 개요 │   메인 영역   │   │📊│      메인 영역        │   ├──────────────────────┤
│ 🗺 웨이퍼맵    │   (약 78%)   │   │🗺│      (약 94%)        │   │                      │
│ 🧠 패턴 분류   │              │   │🧠│                     │   │   메인 영역 (100%)    │
│ 🚨 이상 탐지   │              │   │🚨│                     │   │                      │
│ 🔎 원인 분석   │              │   │🔎│                     │   │   ⚙ 필터 (접힌 expander)│
│ 💡 개선방안    │              │   │💡│                     │   │                      │
│ 📈 모델 검증   │              │   │📈│                     │   │                      │
│ 🎓 도움말·학습 │              │   │🎓│                     │   │                      │
│ ─────────    │              │   │  │                     │   │                      │
│ [필터들]      │              │   │⚙ │ ← 필터는 팝오버로   │   │                      │
└──────────────┴──────────────┘   └──┴─────────────────────┘   └──────────────────────┘
     사이드바 ~22%                    레일 64px 고정
```

- **[B] 아이콘 레일**: 사이드바 폭을 64px로 고정하고 `st.page_link` 를 **이모지 아이콘만** 렌더링한다.
  각 아이콘에는 `help` 툴팁으로 페이지명을 붙여 의미를 잃지 않게 한다. 메인 영역이 약 78% → 94%로
  넓어져, 커미널리티 랭킹처럼 가로가 긴 테이블의 가독성이 크게 개선된다.
- **[C] 모바일**: 사이드바 자체를 접고, 메인 영역 최상단에 **가로 스크롤되는 아이콘 바**를 둔다.
  Streamlit 기본 동작(사이드바가 햄버거 뒤로 숨음)은 네비게이션 접근에 2단계가 필요해 학습 흐름을
  끊으므로, 아이콘 바를 항상 보이게 두는 편이 낫다. 현재 페이지 아이콘은 강조 표시한다.
- 필터는 [B]에서는 `st.popover`, [C]에서는 본문 상단의 접힌 `expander` 로 이동시켜 화면을 절약한다.

### 4A.4 레이아웃 변환 규칙

Streamlit의 `st.columns` 는 좁은 화면에서 세로로 쌓이지만, **비율 컬럼이 쌓이면 순서만 남고
맥락이 끊긴다.** 예컨대 `5_원인_분석` 의 "좌 랭킹 / 우 상세" 구조가 모바일에서 위아래로 쌓이면,
랭킹 테이블을 한참 스크롤해야 상세가 나온다. 따라서 **모바일에서는 컬럼을 탭으로 치환**한다.

| 페이지 | Desktop | Mobile |
|---|---|---|
| `app.py` 개요 | KPI 4개 가로 배치 | KPI 2×2 그리드, 차트 세로 스택 |
| `1_데이터_개요` | 2단(스키마 \| 품질) | 탭 2개 |
| `2_웨이퍼맵_탐색` | 썸네일 5×4 (20장) | 썸네일 2×3 (**6장**), 확대뷰는 탭 전환 |
| `3_패턴_분류_모델` | 좌 혼동행렬 \| 우 recall | 탭(지표 / 혼동행렬 / 해석) |
| `5_원인_분석` | 좌 랭킹 35% \| 우 상세 65% | **탭(① 랭킹 → ② 상세)**, 랭킹에서 항목 선택 시 자동으로 ②탭 활성화 |
| `6_개선방안_기대효과` | 좌 조치안 \| 우 ROI | 탭(조치안 / 기대효과), ROI 입력은 세로 스택 |
| `7_모델_검증` | 카드 3열 | 카드 1열 |
| `8_도움말_학습` | 좌 트리 \| 우 4탭 | §4A.6 전용 레이아웃 |

- 가로가 긴 테이블(커미널리티 랭킹, 스키마 사전)은 모바일에서 **핵심 3개 필드만 남긴 카드 리스트**로
  전환한다. 전체 컬럼은 "표로 보기" 토글 시 가로 스크롤 컨테이너로 제공한다.
- 웨이퍼맵은 정사각 종횡비를 유지하며 `width='stretch'` 로 화면 폭에 맞춘다.

### 4A.5 터치 인터랙션

데스크탑 전제의 상호작용이 모바일에서 조용히 실패하는 경우를 방지한다.

| 문제 | 대응 |
|---|---|
| Plotly **hover 툴팁이 터치에서 동작하지 않음** | 모바일에서는 `hovermode` 대신 **탭(tap) 선택 + 값 라벨 상시 표시**로 전환. 핵심 수치는 차트 밖 캡션에도 병기 |
| 데이터프레임 **행 클릭**으로 드릴다운 | 모바일에서는 `st.selectbox` 로 동일 선택을 제공(행 클릭과 병행) |
| 터치 타깃이 작음 | 버튼·페이지링크·체크박스 최소 44×44px 확보 (CSS) |
| Plotly 확대/이동 제스처가 페이지 스크롤과 충돌 | 모바일에서는 `staticPlot` 에 가깝게 축소하거나 드래그 줌 비활성화, 대신 확대 버튼 제공 |
| 사이드바 스와이프 오작동 | 모바일은 사이드바 미사용(§4A.3 [C])으로 회피 |

### 4A.6 모바일 학습 모드 — "틈틈이 공부"

`8_도움말_학습` 은 모바일 사용 비중이 가장 높은 페이지이므로 전용 설계를 둔다.

**① 카드 분할** — 학습노트 1건을 통째로 스크롤하면 모바일에서 부담이 크다. §5.3 템플릿의
섹션(무엇을 / 핵심 로직 / 왜 이렇게 / 확인 문제)을 **3~5분 분량 카드**로 쪼개고,
`◀ 이전 / 다음 ▶` 버튼으로 한 카드씩 넘긴다. 상단에 `3 / 7` 진행 인디케이터를 표시한다.

**② 진도 이어보기** — 현재 위치를 URL에 기록한다: `?view=mobile&note=commonality&card=3`.
브라우저 히스토리·북마크만으로 이어보기가 되고, 별도 저장소나 로그인이 필요 없다.
읽음 처리한 노트 목록은 `st.query_params` 용량 한계를 고려해 **노트 단위 체크만** 유지한다.
(브라우저 localStorage 연동은 외부 컴포넌트 의존이 생기므로 §11 백로그로 이월)

**③ 모바일 코드 가독성** — 코드는 줄바꿈되면 오히려 읽기 어려우므로 **가로 스크롤 유지**를
원칙으로 하고, 대신 아래를 적용한다.
- 폰트 12px / `line-height 1.5` / 등폭 폰트 고정
- 노트에 인용할 소스는 **함수 단위로 잘라서** 표시(파일 전체 표시 금지). 파일 경로·라인 번호를
  캡션에 병기해 데스크탑에서 원본을 찾을 수 있게 한다
- 각 코드 블록 위에 **한 줄 요약**을 두어, 코드를 다 읽지 않아도 맥락을 잡을 수 있게 한다

**④ 홈 화면 바로가기 안내** — 데스크탑에서 `8_도움말_학습` 상단에 "📱 휴대폰에서 학습하기"
버튼을 두고, 클릭 시 `?view=mobile&page=learning` URL과 QR 코드를 표시한다. 모바일 브라우저의
"홈 화면에 추가"로 저장하면 앱처럼 한 번에 진입할 수 있다. (Streamlit은 완전한 PWA가 아니므로
오프라인 열람은 불가 — 이 한계는 화면에 명시한다.)

**⑤ 학습 전용 모드** — 토글 시 KPI·필터·분석 위젯을 숨기고 학습 콘텐츠만 남겨,
좁은 화면에서 읽기에 집중할 수 있게 한다.

## 5. 코드 학습 지원 체계 (도움말/학습 메뉴) — 신규

### 5.1 목적

이 프로젝트의 코드는 Claude가 작성하지만, **사용자가 나중에 스스로 읽고 이해하고 수정할 수 있어야
코딩 감각이 유지된다.** 따라서 "동작하는 코드"와 별개로 "왜 이렇게 짰는지"를 설명하는 학습 자료를
개발과 동시에 페어로 생산한다. 목표는 두 가지다.

1. 앱을 만드는 과정 자체가 **반도체 도메인 + 데이터 분석 코드**를 배우는 교재가 되게 한다.
2. 포트폴리오 리뷰어(또는 면접관)가 "이 코드 본인이 이해하고 있나요?"라고 물었을 때, 이 메뉴를
   근거로 설명할 수 있게 한다.

### 5.2 구성 원칙

| 원칙 | 내용 |
|---|---|
| **모듈-노트 페어링** | `src/wafermap/` 아래 핵심 모듈 하나당 `docs/learning_notes/` 학습노트 하나. 코드와 설명이 항상 짝을 이룸 |
| **3단계 설명** | ① 무엇을 하는 코드인가(입출력) ② 어떻게 동작하는가(핵심 로직) ③ 왜 이렇게 만들었는가(대안과 트레이드오프) |
| **읽기 순서 로드맵** | 학습 순서 = 개발 마일스톤 순서(M1→M7). 아무 모듈이나 던지지 않고 선행 개념부터 |
| **자가진단** | 노트마다 이해도 확인 질문 2~3개 + 접이식 정답. 단순 "읽었다"가 아니라 "설명할 수 있다"를 목표 |
| **용어사전 연동** | EDS/FDC/SPC/SHAP 등 도메인·통계·ML 용어는 노트 본문에서 바로 사전 항목으로 링크 |
| **실제 코드 인용** | 발췌 코드가 아니라 **저장소의 실제 파일:라인**을 그대로 하이라이트해 보여줌(가짜 예시 코드 지양) |

### 5.4 코드 주석 컨벤션

학습 목적을 지원하기 위해, **일반 프로덕션 코드보다 주석 밀도를 의도적으로 높게** 유지한다.
모든 공개 함수는 다음 docstring 틀을 따른다(한국어, Google 스타일 변형):

```python
def fisher_commonality(case_df, control_df, step_col, equip_col) -> pd.DataFrame:
    """설비별 이상군/정상군 통과율을 비교해 원인 설비 후보를 랭킹한다.

    무엇을: 스텝×설비 교차표를 만들고 Fisher exact test로 유의성을 검정한다.
    어떻게: 설비별 2x2 표(이상군 pass/fail × 해당설비 통과여부)를 만들고,
            scipy.stats.fisher_exact로 p-value, odds ratio를 계산한다.
    왜:    chi-square는 저빈도 셀에서 근사가 깨지는데, 설비 수가 많아지면
            표본이 쪼개져 저빈도 셀이 흔하다. Fisher exact는 정확검정이라 안전하다.

    Args:
        case_df: 이상군 wafer의 fdc_summary 서브셋
        control_df: 정상군 wafer의 fdc_summary 서브셋
    Returns:
        설비별 (odds_ratio, ci_low, ci_high, p_value, p_adj) 랭킹 테이블
    """
```

| **M5** | 개선안·기대효과 | 권고 spec 도출, 반사실 수율 시뮬레이션, ROI 계산기(조정 가능 UI), **학습노트**(`recommend.md`) |
| **M6** | Streamlit 통합 | 9개 화면(개요+8) 동작, 전역 필터, 캐시 최적화, **반응형 3-모드 네비게이션 + 모바일 레이아웃 검증(§4-A)** |
| **M7** | 검증·문서·배포·로컬전환 | 테스트 통과, README·결과 문서, 클라우드 샘플·메모리 검증, `06_local_validation.md` 작성, 로컬 실데이터 재검증 절차 확인 |

## 10. 리스크와 대응

| 시뮬레이터가 너무 쉬워 분석이 자명 | 분석 역량 미증명 | 교락·노이즈·위양성/위음성·설비 baseline 편차·distractor 스텝(P045) 의도적 주입 |
| Streamlit Cloud 1GB 메모리 | 배포 실패 | 샘플 데이터셋 + 사전학습 아티팩트, 앱 내 학습 금지, 메모리 프로파일링 |
| 개발 컨테이너 네트워크 차단 | 실데이터 검증 불가 | 합성 경로로 전체 개발, 사용자 로컬에서 실데이터 검증 단계 별도(§2.3) |
| 상관을 인과로 오독 | 잘못된 개선안 | 층화 분석, 인과 가정 UI 명시, 기대효과에 신뢰구간·가정 병기 |
| ROI 가정치가 실제와 괴리 | 개선효과 신뢰성 저하 | 모든 가정치에 출처 배지 + 앱 내 즉시 조정 가능 UI(§3 M5.4) |
| 학습노트가 코드와 어긋남(드리프트) | 학습 자료 신뢰성 저하 | 코드는 실제 소스를 실시간 인용(§5.5)해 하드코딩 복붙 방지, 마일스톤 완료 기준에 노트 갱신 포함 |
| 172,950장 웨이퍼맵 갤러리 렌더링 | 로딩 지연, 클라우드 메모리 초과 | 썸네일 사전 생성 + 페이지네이션(페이지당 20장) + 서버사이드 샘플링(§4.5) |
| 하위 페이지를 상위 선택 없이 바로 열람 | 빈 화면·이탈 | §4.4 전역 상태 기본값으로 항상 합리적 프리셋 제공, 안내 배너로 상위 페이지 유도 |
| red/green 색상이 색각이상 사용자에게 구분 어려움 | 접근성 저하 | blue/orange 팔레트 + 아이콘/명도 보조 표시(§4.8) |
| 데이터 소스 토글 시 캐시 미갱신으로 옛 결과 노출 | 결과 신뢰성 저하 | 캐시 키에 `data_source` 포함해 자동 분리, 전환 배너 노출(§4.7) |
| 첫 방문자가 8개 페이지를 다 못 보고 이탈 | 포트폴리오 전달력 저하 | `app.py`에 KPI 요약 + `3분 가이드 투어` 버튼(§4.9) |
