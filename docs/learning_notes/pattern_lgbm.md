# LightGBM 패턴 분류 — 1,000 대 1 불균형과 싸우기

## 이 코드는 무엇을 하나

**입력**: 웨이퍼당 99개 기하 피처
**출력**: 9종 패턴 중 하나 (`"Edge-Ring"`, `"Center"`, ...)

그런데 이 문제의 진짜 난이도는 분류 자체가 아니라 **데이터 분포**에 있다.

```
none        5,115장  ████████████████████████████████████████████  85.25%
Edge-Ring     336장  ███                                            5.60%
Edge-Loc      180장  ██                                             3.00%
Center        149장  █                                              2.48%
Loc           125장  █                                              2.08%
Scratch        41장                                                 0.68%
Random         30장                                                 0.50%
Donut          19장                                                 0.32%
Near-full       5장                                                 0.08%   ← 1,000 : 1
```

**아무 생각 없이 학습하면 모델은 "전부 none"이라고 답한다.** 그래도 정확도가
85%나 나오기 때문이다. 이 모듈은 그 함정을 피하는 방법에 관한 것이다.

## 핵심 로직

### 대응 1: 평가 지표를 macro-F1로

가장 먼저 바꿔야 하는 건 모델이 아니라 **자(尺)** 다.

| 지표 | "전부 none" 모델의 점수 | 쓸모 |
|---|---|---|
| accuracy | **0.85** | ❌ 높게 나와서 속는다 |
| macro-F1 | **0.10** | ✅ 8개 클래스를 놓친 걸 잡아낸다 |

macro-F1은 클래스별 F1을 **단순 평균**한다. 표본 수로 가중하지 않기 때문에,
5장짜리 Near-full을 통째로 놓치면 점수의 1/9이 날아간다.

코드에서도 accuracy는 참고용으로만 출력하고 경고를 붙인다.

```python
f"accuracy : {self.accuracy:.4f}  (참고용 — 불균형 때문에 의미가 약하다)",
```

### 대응 2: 클래스 가중치

희소 클래스의 오답에 더 큰 벌점을 준다.

```python
counts = np.bincount(y_train, minlength=len(PATTERN_LABELS)).astype(float)
weights_per_class = len(y_train) / (len(PATTERN_LABELS) * np.maximum(counts, 1))
sample_weight = weights_per_class[y_train]
```

`전체 표본 수 / (클래스 수 × 그 클래스 표본 수)` 라는 표준 공식이다.
직관: **각 클래스가 전체 손실에 똑같이 기여하도록** 만든다.

```
none      5,115장 → 가중치 0.13   (많으니 하나당 값어치를 낮춘다)
Near-full     5장 → 가중치 133    (적으니 하나당 값어치를 크게)
```

`np.maximum(counts, 1)`은 fold에 그 클래스가 한 장도 안 들어갔을 때
0으로 나누는 걸 막는 안전장치다.

### 대응 3: 회전·미러 증강 — 그리고 **효과가 없다는 발견**

웨이퍼는 원판이라 90° 돌려도 여전히 같은 불량이다. 물리적으로 타당한 증강이다.

```python
transforms = [(k, flip) for k in range(4) for flip in (False, True)][1:]
```

4가지 회전 × 2가지 반전 = 8가지 조합에서, 항등변환(`[1:]`로 잘라냄)을 뺀 7가지를 쓴다.

그런데 실제로 측정해 보니 이런 결과가 나왔다.

```
증강 없음   macro-F1 0.9775 ± 0.0029   (시드 0,1,2: 0.9741, 0.9771, 0.9812)
증강 200    macro-F1 0.9765 ± 0.0014   (시드 0,1,2: 0.9745, 0.9775, 0.9775)
────────────────────────────────────────────────────
차이: -0.0009        시드 간 표준편차: 0.0023
```

**차이(-0.0009)가 시드 간 산포(0.0023)보다 작다 → 노이즈다.**

이건 중요한 교훈이다. 처음 한 번만 돌렸을 때는 0.9741 vs 0.9707로 나와서
"증강이 오히려 해롭다"고 결론 내릴 뻔했다. 시드를 3개로 늘려 보니 **둘 다
측정 오차 범위 안**이었다.

> 💡 **효과 크기를 노이즈와 비교하지 않은 비교는 비교가 아니다.**
> 0.003 차이를 보고 결론을 내리려면, 먼저 "아무것도 안 바꿔도 0.003쯤은 흔들리는가"를
> 확인해야 한다.

그래서 기본값을 꺼 두되(측정된 이득이 없으므로) 코드는 남겼다.
실측 WM-811K는 Near-full이 172,950장 중 149장이고 라벨 노이즈도 있어
상황이 다르므로, 그때 다시 재야 한다.

### 대응 4: 누출 방지 — 증강은 반드시 fold 안에서 ★

이게 가장 틀리기 쉬운 부분이다.

```
❌ 잘못된 순서                     ✅ 올바른 순서 (코드가 하는 것)
전체 데이터 증강                   fold 분할
   ↓                                  ↓
fold 분할                          학습 fold만 증강
   ↓                                  ↓
원본이 학습에, 회전본이 검증에      검증 fold는 원본 그대로
   ↓                                  ↓
"이미 본 웨이퍼"를 맞히는 셈        정직한 성능 추정
→ 점수가 부풀려짐
```

코드에서는 fold를 나눈 **뒤에** 증강한다.

```python
    for fold, (train_idx, valid_idx) in enumerate(skf.split(X, y), start=1):
        X_train, y_train = X[train_idx], y[train_idx]
```

그리고 새로 만들어진 것만 피처를 다시 뽑는다.

```python
            new_ids = {w for w in aug_maps if w not in train_maps}
```

### 대응 5: 계층 교차검증(StratifiedKFold)

```python
    skf = StratifiedKFold(n_splits=n_splits, shuffle=True, random_state=seed)
```

일반 KFold를 쓰면 Near-full 5장이 한 fold에 몰려서, 나머지 4개 fold에는
그 클래스가 **아예 없는** 상황이 생긴다. `Stratified`는 각 fold의 클래스 비율을
전체와 같게 유지한다. 극단적 불균형에서는 선택이 아니라 필수다.

## 결과 읽기

```
macro-F1 : 0.9741

클래스               F1   recall      표본
--------------------------------------
Center         0.980    1.000     149
Donut          1.000    1.000      19
Edge-Loc       0.994    0.994     180
Edge-Ring      1.000    1.000     336
Loc            0.911    0.896     125
Near-full      1.000    1.000       5
Random         1.000    1.000      30
Scratch        0.883    0.829      41
none           0.999    0.999   5,115
```

### 이 숫자를 어떻게 받아들여야 하나 ⚠️

**0.97은 합성 데이터 점수이고, 실측 WM-811K에서는 이만큼 나오지 않는다.**
포트폴리오에서 "웨이퍼 맵 분류 macro-F1 0.97"이라고 쓰면 오해를 부른다. 이유는 셋이다.

1. 합성 맵은 깨끗한 수식(가우시안, 시그모이드)에서 나왔다. 실측은 훨씬 지저분하다.
2. 실측 WM-811K는 사람이 붙인 라벨이라 **오라벨이 알려져 있다.**
   모델이 맞혀도 라벨이 틀렸으면 오답으로 집계된다.
3. Near-full은 5장 중 5장을 맞혔지만, n=5로는 아무것도 증명하지 못한다.

정직한 서술은 이렇다:
> "합성 데이터에서 파이프라인이 정상 동작함을 확인(macro-F1 0.97). 실측 WM-811K
> 기준 성능은 로컬 검증 단계에서 별도 측정 예정."

### 혼동행렬이 말해 주는 것

```
  Loc  →  Center 6건,  Scratch 4건
Scratch →  Loc 5건
```

오답이 **물리적으로 혼동될 만한 쌍**에 몰려 있다. Loc(국부 뭉침)과 Scratch(선형)는
둘 다 국부 불량이고, 작은 스크래치는 실제로 Loc처럼 보인다.
모델이 무작위로 틀리는 게 아니라 **어려운 것을 어려워한다**는 뜻이라, 좋은 신호다.

### 피처 중요도 상위

```
fail_centroid_r         34,572   ← 불량 무게중심의 반경 (중심이냐 엣지냐)
outer2_ratio            15,478   ← 최외곽 2링 비율 (Edge-Ring)
cluster_count_norm      13,803   ← 덩어리 개수 (Random 판별)
angular_concentration   12,606   ← 각도 쏠림 (Edge-Loc)
```

설계에서 "이 피처가 이 패턴을 가를 것"이라고 의도한 것들이 그대로 상위에 올라왔다.
피처 엔지니어링이 의도대로 작동했다는 증거다.

## 왜 이렇게 만들었나 — 설계 선택과 대안

### 선택 1: 왜 `cross_validate`와 `fit_final`을 분리했나?

두 함수는 목적이 다르다.

| | `cross_validate` | `fit_final` |
|---|---|---|
| 목적 | 성능을 **추정** | 배포용 모델 생산 |
| 데이터 | fold로 나눠 씀 | 전체 사용 |
| 산출물 | 점수 | 모델 파일 |

한 함수에 섞으면 "검증 점수를 낸 모델"과 "실제 배포한 모델"이 달라지는데,
그걸 인지하지 못한 채 "이 모델의 성능은 0.97"이라고 말하게 된다. 엄밀히는
0.97은 *같은 방식으로 학습한 모델들*의 평균 성능이지 배포 모델의 성능이 아니다.
함수를 나누면 이 구분이 코드에 드러난다.

### 선택 2: 왜 보수적인 하이퍼파라미터인가?

```python
    "learning_rate": 0.05,
    "num_leaves": 31,
    "min_child_samples": 10,
    "feature_fraction": 0.7,
```

데이터가 6,000장인데 피처가 99개다. 트리를 깊게 키우면 Donut 19장,
Near-full 5장 같은 클래스는 **개별 웨이퍼를 통째로 외워 버린다.**
`min_child_samples=10`은 잎 하나에 최소 10장을 요구해서 그걸 막는다.

### 선택 3: 왜 하이퍼파라미터 튜닝을 안 했나?

이미 macro-F1 0.97이라 튜닝의 여지가 거의 없고, **합성 데이터에서 튜닝한 값이
실측에서도 최적일 이유가 없다.** 실측 데이터를 확보한 뒤 튜닝하는 게 순서다.
지금 튜닝하면 합성 데이터의 특성에 과적합된 설정을 얻게 된다.

## 확인 문제

**1.** "전부 none"이라고 답하는 모델의 macro-F1은 대략 얼마인가?

<details><summary>정답</summary>

none의 F1만 거의 1.0이고 나머지 8개는 0이므로, **약 1/9 ≈ 0.11**이다.
accuracy는 0.85지만 macro-F1은 0.11 — 두 지표가 이렇게 갈리는 것이
불균형 문제에서 지표 선택이 중요한 이유다.
</details>

**2.** 증강을 fold 분할 **전에** 하면 검증 점수는 어떻게 되고, 왜 그런가?

<details><summary>정답</summary>

**부풀려진다.** 같은 웨이퍼의 원본이 학습 fold에, 90° 회전본이 검증 fold에
들어갈 수 있기 때문이다. 회전본은 원본과 거의 같은 피처 값을 가지므로,
모델은 사실상 "이미 본 웨이퍼"를 맞히는 셈이 된다.
이런 종류의 오류를 **데이터 누출(data leakage)** 이라고 한다.
</details>

**3.** 증강 효과가 -0.0009였는데 "증강이 해롭다"고 결론 내리면 안 되는 이유는?

<details><summary>정답</summary>

시드만 바꿔도 macro-F1이 0.9741~0.9812로 **0.007이나 흔들린다**(표준편차 0.0023).
-0.0009는 그 산포보다 훨씬 작으므로 측정 오차와 구분되지 않는다.
결론은 "해롭다"가 아니라 **"효과를 측정할 수 없다"** 이다.
차이를 주장하려면 효과 크기가 노이즈보다 커야 한다.
</details>

**4.** 실측 WM-811K로 옮겼을 때 macro-F1이 0.97보다 낮아질 것으로 예상하는 이유 세 가지는?

<details><summary>정답</summary>

1. 합성 맵은 깨끗한 수식에서 생성되어 패턴 경계가 뚜렷하지만, 실측은 지저분하다
2. 실측 라벨은 사람이 붙인 것이라 **오라벨이 존재한다** — 모델이 맞혀도 오답 처리된다
3. 실측은 맵 크기가 제각각이라 피처 추출의 어려움이 더 크다
   (그래서 크기 불변성을 미리 확보해 둔 것이다 → `geometry.md` 선택 2)
</details>

## 더 알아보기

- **macro / micro / weighted 평균**: micro는 표본 수로 가중해 accuracy에 가깝고,
  weighted도 마찬가지다. 희소 클래스를 보려면 반드시 **macro**
- **StratifiedKFold vs KFold**: 분류 문제에서는 거의 항상 Stratified가 맞다
- **데이터 누출(data leakage)**: 검증 데이터의 정보가 학습에 새어 드는 모든 경우.
  증강, 정규화(전체 평균으로 스케일링), 시계열에서 미래 정보 사용 등이 대표적
- 관련 모듈: [`geometry.md`](geometry.md) — 여기서 만든 피처를 쓴다 /
  [`pattern_cnn.md`](pattern_cnn.md) — 같은 문제를 딥러닝으로
