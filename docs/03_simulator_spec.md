# 03. 시뮬레이터 명세 — 무엇을 어떻게 심는가

이 프로젝트의 데이터는 **원인을 일부러 심어서** 만든다. 그래서 정답지가 있고,
분석 방법을 채점할 수 있다. 이 문서는 **무엇을 심고, 왜 그렇게 심는지**를 적는다.

관련 코드: `src/wafermap/config.py` (규칙), `src/wafermap/data/fdc_simulator.py` (주입),
`src/wafermap/data/synth_wafer.py` (맵 생성)

파라미터 전체 목록은 `docs/02_data_dictionary.md`에 있다 (코드에서 생성).

---

## 0. 왜 합성 데이터를 쓰나 ★

공개된 웨이퍼 맵 데이터(WM-811K)는 **맵과 라벨만** 있다. FDC 센서 데이터도,
"어느 챔버가 원인이었는가"라는 정답도 없다. 세상에 없는 정보다.

정답이 없으면 **분석이 맞았는지 알 수 없다.** "이 챔버가 원인 같습니다"라고
말할 수는 있어도, 그게 맞는지 틀리는지를 잴 방법이 없다.

그래서 이 프로젝트는 순서를 뒤집었다.

```
   원인을 심는다  →  데이터가 나온다  →  분석이 그 원인을 찾아내는가?
   (정답지 보관)                          (채점 가능)
```

**정답지(`ground_truth`)는 분석 모델에 절대 넣지 않는다.** 채점에만 쓴다.

### 대가

합성 데이터는 실측보다 **신호가 깨끗하다.** 결측도, 센서 드리프트도, 레시피
변경도 섞여 있지 않다. **여기서 나온 성능은 모두 상한선이다.**
그 한계를 어떻게 다루는지는 `docs/06_local_validation.md`에 있다.

## 1. 만들어지는 것

기본 설정: 웨이퍼 **6,000장** = **240 lot** × 25장, **121일**치

| 산출물 | 내용 |
|---|---|
| `wafer_master.parquet` | 웨이퍼 이력 (수율·라벨·검사 설비) |
| `die_map.npz` | 웨이퍼별 2차원 맵 배열 |
| `fdc_summary.parquet` | 웨이퍼 × 스텝 센서 요약통계 |
| `fdc_trace.parquet` | 원파형 (60초를 60점) |
| `ground_truth.parquet` | **정답지** |
| `excursions.parquet` | 이상 구간 기록 (언제부터 언제까지) |

시간 구조:
- 스텝 간격 **6시간**, 공정 9스텝 → 투입에서 마지막 공정까지 54시간
- 마지막 공정에서 EDS까지 **12시간**
- 즉 **사이클 타임 66시간**. 관리도의 EDS 시각과 원인의 공정 시각이 이만큼 어긋난다

## 2. 다섯 가지 원인 경로

같은 맵 모양이 여러 원인에서 나온다. 이것이 이 프로젝트의 핵심 난점이고,
시뮬레이터는 그 상황을 일부러 만든다.

| 경로 | 무엇 | 어떤 패턴에 얼마나 섞나 |
|---|---|---|
| `process` | 파라미터가 지속적으로 이탈 | 나머지 전부 |
| `test` | 프로브 카드 문제 | Edge-Ring 30% · Loc 25% |
| `spike` | 2~3초 순간 이탈 | Edge-Loc 20% |
| `drift` | 60초 동안 서서히 밀림 | Edge-Loc 18% |
| `interaction` | 두 공정의 조합 | Center 30% |

### 2.1 공정 기인 (process)

파라미터를 σ 배수만큼 밀어 둔다.

| 패턴 | 스텝 | 흔드는 파라미터 (σ 배수) |
|---|---|---|
| Center | P050 CMP | `down_force` +4.0 · `center_zone_pressure` +3.5 · `pad_life` 92% 소진 |
| Donut | P030 증착 | `susceptor_temp_mid_delta` +4.0 · `precursor_flow` −2.5 |
| Edge-Ring | P020 식각 | `edge_ring_rf_hours` 95% 소진 · `chamber_pressure` +3.0 · `o2_flow` −2.0 |
| Edge-Loc | P060 세정 | `chuck_edge_temp_dev` +3.5 · `particle_count` +3.0 |
| Loc | P010 포토 | `focus_offset` +4.0 · `defect_adder_count` +3.0 |
| Scratch | P050 CMP | `slurry_flow` −3.5 · `conditioning_time` −3.0 · `slurry_particle_count` +3.5 |
| Near-full | P040 이온주입 | `dose` +8.0 · `beam_current` −5.0 |
| **Random** | **없음** | **원인 설비 없음이 정답** |
| **none** | — | 정상 |

> **Random을 왜 넣었나 ★**: 분석 도구는 "원인을 찾는 능력"만큼 **"원인이 없을 때
> 없다고 말하는 능력"** 이 중요하다. Random에 대해 어떤 챔버를 지목하면 오답이다.

> **Near-full의 σ가 왜 8.0인가**: 레시피를 잘못 넣은 수준의 사고를 흉내 낸 것이다.
> 미세한 이탈이 아니라 명백한 사고라서, 이건 찾기 쉬워야 정상이다.

### 2.2 검사 기인 (test)

공정은 멀쩡한데 **검사가 불량을 만드는** 경우다. 분석 단위가 설비가 아니라
**프로브 카드**라는 점이 다르다 (`explicit_units`).

| 패턴 | 기구 | 흔드는 파라미터 |
|---|---|---|
| Edge-Ring | 니들 오염·마모로 접촉 저항 상승 → 평탄도가 나쁜 최외곽 die부터 접촉이 끊긴다 | `touchdown_count` 93% · `contact_resistance` +3.5 · `probe_overdrive` −3.0 |
| Loc | 카드 정렬 틀어짐 → 특정 site의 니들이 pad를 빗나간다. 같은 카드로 측정한 웨이퍼마다 **같은 위치**에 fail | `probe_mark_offset` +4.0 · `contact_resistance` +2.0 · `test_time` +2.5 |

**맵으로는 공정 기인과 구분되지 않는다.** 그것이 요점이다.
조치는 완전히 다르다 — 카드 세정은 몇 시간, 챔버 PM은 며칠이다.

### 2.3 순간 스파이크 (spike)

Edge-Loc, P060 세정. `bath_temp`를 **7σ만큼 3초간** 튀긴다.

세정조 히터가 순간 과열되면 웨이퍼 가장자리 메니스커스 접촉부에서만 자연산화막이
과도하게 제거된다. **60초 평균으로는 0.35σ밖에 안 움직여** 요약통계에서 묻힌다.

### 2.4 서서히 밀림 (drift)

Edge-Loc, P060 세정. `bath_temp`가 60초 동안 **8.6σ 폭으로** 선형 이동한다.

> **8.6이라는 숫자는 어디서 나왔나 ★**
> 임의로 고른 값이 아니다. **스파이크와 표준편차가 같아지도록 역산했다.**
> 그래야 "요약통계로는 둘을 못 가른다 — 파형의 *모양*을 봐야 갈린다"는 문제가
> 실제로 성립한다. 두 경로의 산포가 다르면 `_std` 하나로 갈려 버려서
> 형상 피처를 만들 이유가 사라진다.
>
> 측정 결과: 두 경로를 가르는 단변량 AUC가 최소 0.901(`_min`)에서
> 0.969(`settle_time`)까지 올라갔다.

### 2.5 교호작용 (interaction)

Center 패턴. **P030의 `precursor_flow` × P050의 `down_force`.**

증착이 두께 상한 쪽(`sign_b = -1`이므로 반대 방향)인데 CMP 제거량이 하한 쪽이면
중심부에 잔막이 남는다. 반대 조합이면 중심부가 과연마된다.

- 흔드는 폭: **1.3~1.9σ** — 일부러 작게 둔다
- 설비 조합 고정: `CVD-02/ch1` × `CMP-02/ch3`

> **왜 1.3~1.9σ인가 ★**: **각 파라미터가 규격 안에 머물러야** 하기 때문이다.
> 단독으로는 이상으로 잡히지 않고, 조합일 때만 불량이 나야 "한 축씩 보는 분석으로는
> 절대 못 찾는다"는 상황이 성립한다.
>
> 측정 결과: 그 설비 조합의 초과 불량률은 **+36%p로 1위**였는데,
> **각 챔버를 따로 보면 0.0%** 였다.

## 3. 현실의 지저분함을 일부러 넣는다

`DEFAULT_DIFFICULTY`가 이것을 조절한다. **없으면 문제가 너무 쉬워진다.**

| 설정 | 값 | 무엇을 흉내 내나 |
|---|---:|---|
| `false_positive_rate` | 0.06 | 원인을 심었는데 불량이 안 난 경우. 섭동이 항상 불량으로 이어지지는 않는다 |
| `unexplained_rate` | 0.10 | 원인을 안 심었는데 불량인 경우. 현실의 "원인 미상" 몫이다 |
| `confound_rate` | 0.25 | 원인이 둘 이상 겹친 경우. 단독 귀속이 불가능해진다 |
| `equip_bias_sigma` | 0.8 | 설비마다 원래 조금씩 다르다. **정상 설비도 값이 다르다**는 뜻이라 "값이 다르면 원인"이라는 순진한 접근이 실패한다 |
| `drift_sigma_per_pm` | 1.2 | PM 주기 동안 값이 서서히 밀린다 |
| `severity_range` | 0.55~1.35 | 같은 원인이라도 심각도가 제각각이다 |

> **`unexplained_rate`가 10%인 이유**: 현실에서 모든 불량의 원인이 밝혀지지는
> 않는다. 100% 설명 가능한 데이터로 분석을 검증하면 **찾을 수 있는 것만 찾는
> 도구**가 만들어진다.

## 4. 원파형은 어떻게 만드나

`TRACE_POINTS = 60`, `TRACE_SECONDS = 60.0` — 60초를 60점으로 본다.

```python
settle = 1.0 - 0.03 * np.exp(-t_sec / 4.0)          # 초반 3% 안정화
matrix = base[:, None] * settle[None, :] + noise     # 파형
steady = matrix[:, int(TRACE_POINTS * 0.4):]         # 40% 이후가 정상 구간
df[f"{pname}_mean"] = steady.mean(axis=1)            # 요약통계를 파형에서 계산
```

### 요약통계를 파형에서 계산하는 이유 ★

처음에는 요약통계와 파형을 **따로** 만들었다. 그랬더니 자기모순이 생겼다 —
그래프는 68.9℃ 스파이크를 보여 주는데 `_max`는 65.1이었다.

그 상태에서 "형상 피처가 요약통계보다 낫다(0.594 → 0.964)"는 결과가 나왔는데,
**그건 형상 피처가 좋아서가 아니라 요약통계가 파형과 무관한 값이었기 때문**이었다.
파형에서 다시 계산하니 `_std`만으로도 0.936이 나왔다.

이 발견 때문에 M5.5-② 마일스톤의 주장 자체를 다시 썼다.
자세한 경위는 `docs/04_results.md`.

### 초반 3% 안정화의 함정

처음에는 `base * (1 - exp(-t/6))`으로 **0에서부터 올라오게** 만들었다.
그랬더니 정상 웨이퍼도 `time_above`(임계 초과 시간)가 6초씩 나왔다 —
상승 구간이 임계를 넘었기 때문이다.

두 가지를 고쳤다: 안정화 폭을 3%로 줄이고, 형상 피처가 **추세를 제거한 뒤**
임계를 판정하도록 했다.

## 5. 실측 맵 모드 (`--source real`)

`build_dataset.py --source real`은 **실측 맵 + 합성 공정 이력**을 만든다.
라벨별로 짝지어 붙인다 — "Edge-Ring 실측 맵"에 "Edge-Ring을 유발한 식각 이력"이 붙는다.

**⚠️ 원인 정답지는 여전히 합성이다.** WM-811K에는 FDC가 없으므로
M3~M5는 이 모드에서도 실측 재측정이 아니다. `docs/06_local_validation.md` §0 참고.

## 6. 일부러 넣지 않은 것

| 안 넣은 것 | 왜 |
|---|---|
| **Bin 코드별 불량 사유** | 정의(`BIN_CODES`)만 두고 부여하지 않는다. 화면은 풍부해지지만 분석 결론이 바뀌지 않는다 — 백로그 M5.5-④ |
| **die 단위 측정값** | 위와 같은 이유 |
| **결측·센서 고장** | 실측에는 있다. 넣으면 전처리 검증이 늘지만 인과 채점이 흐려진다 |
| **레시피 변경 이력** | 분포가 통째로 이동하는 상황. 현재 스코프 밖 |
| **다중 제품·노드** | 단일 제품(DDR5 16Gb, 1z-nm)으로 고정했다. 섞으면 규격이 달라 분석 자체가 달라진다 |
| **재작업(rework)** | 같은 웨이퍼가 같은 스텝을 두 번 지나는 경우 |

이것들은 **모르고 뺀 것이 아니라 알고 뺀 것**이다.
넣으면 데이터는 현실적이 되지만, 분석 방법의 채점이 흐려진다.

## 7. 재현성

```bash
python scripts/build_dataset.py                    # 기본 시드 20260817
python scripts/build_dataset.py --seed 42
python scripts/run_seed_study.py                   # 여러 시드로 분포 재기
```

> **시드 하나를 성능이라고 부르지 말 것 ★**
> 이 프로젝트에서 "원인 챔버 Top-1 100%"라고 적어 두었던 수치가 다른 시드에서는
> 67%였다. 8개 시드로 재니 **67% ± 17%**(최소 33%, 최대 83%)였다.
>
> 수치를 인용할 때는 반드시 `run_seed_study.py`로 분포를 함께 봐야 한다.
> 자세한 경위는 `docs/04_results.md`의 "⚠️ 시드 재현성" 절.
